## PR 1 - AG-582: view quick status from the tray

### 1.1 Cross-window navigation intent (the primitive)

`revealMainWindow()` -> `reveal_popover_window` (`lib.rs:2740`) takes no
argument and does not navigate: it shows the 1280x800 window on whatever pane
was last active. `Tray.tsx`'s rows are not clickable at all, and
`SecurityCard.onOpen` is wired to the same bare `expand` while its docstring
(`Tray.tsx:379-382`) promises "the pane it opens has the detail this card
deliberately does not try to fit". That promise is not implemented.

Follow the `quit-requested` precedent exactly - Rust buffers, the window
consumes:

- `reveal_popover_window(app, intent: Option<NavIntent>)`; buffer the intent
  the way `PENDING_QUIT_TOOLS` is buffered, then emit `navigate`.
- `NavIntent` serialises to `SidebarView` (`Sidebar.tsx:16`), which already has
  the four cases needed: `overview`, `security`, `settings`, `app{slug}`. No
  new vocabulary.
- `NewUiApp` grows a `listen("navigate")` beside its four existing listeners
  and calls `setView` (`NewUiApp.tsx:224`).
- Buffer-then-emit matters: the window may not be listening yet on a cold
  reveal. Same reason `quit-requested` buffers.

Unblocks, in this PR: `SecurityCard.onOpen` -> `{kind:"security"}`, and Switch
organization below. Consumed later by AG-584's rows and alerts, and AG-598's
dashboard action.

### 1.2 Switch organization

AC: "Switch organization opens the organization selector." There is no such
control in the tray footer today.

`onSwitchOrg` already exists in the window shell and calls
`settings.openSwitchOrg()` (`NewUiApp.tsx:1867`). So: a footer menu entry ->
navigate intent -> that handler. No new dialog, and the tray must not grow its
own org picker - two selectors over one setting is the divergence principle 2
warns about, one level up.

Check whether the drawn footer menu (`744:38192`) has room, or whether the org
name in the footer becomes the affordance. The frame draws the org name as a
label beside a `users` glyph, not as a button.

### 1.3 WITHDRAWN - Linux's unconditional quit is correct

**This item was wrong, and the code says so at the site.** It read
`app.exit(0)` on Linux against a buffered chooser on macOS/Windows and called
it an AC breach and a principle-5 exemption.

`request_quit`'s own comment answers it: on Linux the engine is a **detached
helper daemon that outlives this process**. Quitting the GUI stops no routing
and leaves no config aimed at a dead relay, so there is no question to ask -
and asking would be worse than silent, because the "disconnect and quit" branch
would tear down routing the user never needed to lose. The comment also records
that someone removed the gate once, reasoning from AG-596 exactly as this item
did, and that it was a regression: *"Do not remove it again."*

Kept as a withdrawal rather than deleted, because `docs/review-flow-tray.md`
still lists it as a dead end and this plan repeated it from there. Two documents
asserting a bug that a third document and the code both refute is how it gets
"fixed" a second time.

### 1.4 FIXED UPSTREAM - the `Not protected - Checking` dead end

`refreshVerdicts` swallows failure (`TrayApp.tsx:88` `.catch(() => null)`) and
leaves the verdict map empty, which `verdict.ts:79` renders as
`{kind:"not-protected", detail:"Checking"}` on **every** row - amber, with the
master card reading `0 of N`. The poll only re-fetches when the tools/proxy
signature changed (`TrayApp.tsx:123`), so on an idle machine one failed sweep
at first load persists until a tools/proxy change or a `proxy-state-changed`
event. The tray has no refresh affordance - the window's rail has `onRefresh`,
this surface has none.

Two problems, both this ticket's:

- The screen is simultaneously wrong about every row and about the headline
  count. Per principle 6 a failed sweep is *no reading*, not "not protected":
  it must not borrow a routing verdict's copy, the same correction
  `accountUnread` already made one prop up (`Tray.tsx:97-101`).
- `Checking` is not one of the reasons the AC enumerates (Reopen required,
  Configuration changed, Verification failed, Access problem, Connection
  problem). A failed sweep needs its own state and a way out of it.

**Closed before this plan was acted on.** `TrayApp` now carries a
`verdictsRead` ref and the poll re-sweeps on `changed || !verdictsRead.current`,
so a failed read retries every five seconds instead of persisting until
something else moved. Its comment names this exact scenario, down to the
`0 of N` master card and the absent refresh affordance.

What remains is not a dead end but a deliberate trade, argued at
`verdict.ts:70-73`: an unanswered row says `Checking` in amber rather than
reading `Protected` off a config file, because a saved configuration does not
produce On (AG-562). So "Checking" stays outside the AC's reason vocabulary on
purpose - it is the absence of a verdict, not one of them.

### 1.5 ALREADY SATISFIED - "a routing control appears only for a validated integration"

Audited 2026-09-08. `Verdict.state` is the closed set
`not_installed | on | off | needs_attention` (`api.ts:445`), and `TrayApp`
filters rows on `t.status.kind !== "not_installed"` before building them, so the
only integrations without a switch are the ones with nothing to route - drawn in
their own section, whose absent switch is recorded at `Tray.tsx:55-57`.

Every remaining row's switch is driven by intent
(`connected | drifted | overridden`), not by the verdict, which is principle 2
and the bug `lib/groups.ts` documents. No change.

### 1.6 `POPOVER_VISIBLE` leaks true, disabling the on-open reconcile

The flag is cleared only at `lib.rs:3161` (CloseRequested) and `:3785`
(icon-click hide), and `TrayApp`'s own hides never clear it: `expand`
(`TrayApp.tsx:313`) and quit (`:334`) call `getCurrentWindow().hide()`
directly. The `Focused(true)` arm that sets it is also not window-scoped - the
Linux `main` branch above it (`lib.rs:3143`) does not `return`, so focusing the
main window sets it too.

Consequence: after one Expand, or once the main window has been focused, the
next tray open finds the flag already `true` and skips
`provider::reconcile_enabled()` - which `lib.rs:3163-3181` documents as how a
tool installed since launch gets wired up without a relaunch. Read from the
code, not observed running, so confirm before fixing.

### 1.7 FIXED UPSTREAM - transient UI state surviving a hide/show cycle

The tray window is hidden, not destroyed, so `menuOpen` (`TrayApp.tsx:70`),
`notInstalledOpen`, and an unresolved `routing.prompt` dialog all come back on
the next open. Click the ellipsis, dismiss with the tray icon, click again: the
menu is still open over the list. Only `redetect` runs on the visibility edge
(`TrayApp.tsx:153-155`).

**Closed before this plan was acted on**, for the menu: the
`visibilitychange` handler calls `setMenuOpen(false)` on hide, with a comment
naming the same scenario.

Dialogs deliberately persist, and that is now the right answer rather than an
omission. `TrayApp` pins the popover open while one is on screen (see the
Landed section), so blur can no longer dismiss the window out from under an
unanswered question - and a config-overwrite confirmation that returns on the
next open is a question that is still genuinely pending. `notInstalledOpen`
persists too, harmlessly.

### 1.8 Master card copy: raise, do not decide

The AC says the compact experience shows "On, Off, or Needs attention". The
frames draw "Gate is protecting you" / "Partially routed" / "Not protected"
over an `On - 6 of 8 tools routing` sub-line, and that is what ships
(`Tray.tsx:195-200`).

**Decision 2026-09-07: keep the drawn copy.** CLAUDE.md's standing instruction
is that the file wins on copy, and the sub-line already carries the On/Off the
AC asks for. Add to `docs/figma-questions-for-design.md` as question 18 - the
AC-vs-frame conflict, with the argument above - rather than resolving it by
eye. That file's two decided exceptions stay decided; this is a candidate
third, which the entry says to raise.

A concrete example for that entry, from the 2026-09-07 render: engine on with
nothing routed draws `Not protected` over `On - 0 of 8 tools routing`. Both
halves are right - the phrase reports observed state, the sub-line reports
intent, which is principle 2 - and read together they look like a
contradiction. If design wants one voice on that card, this is the case to show
them.

Also raise there, from the flow audit: the drawn `Not protected - 3d ago`
timestamp (`738:37562`) that no `Verdict` field can produce; whether the absent
blur-dismiss is a decision or a regression; and that `SecurityCard` meets an
AG-582 AC with a component no tray frame draws, so the frames are now behind
the build on that row.

## PR 2 - AG-584: view tool metrics from the tray

Both halves of the activity line are built (#219, #220): alerts live from the
AG-578 feed, messages held behind `lib/toolMessages.ts`'s 45s TTL, with a
skeleton in flight, nothing at all for no reading, and "No alerts" for a
measured zero. What follows is what the ACs still ask for.

### The data half: answered, and what it costs (2026-09-08)

Every open data question on AG-584 was answerable from the two repos. Recorded
here because the answers change the design rather than just filling a blank.

**The reading already carries its period.** `window { from, to }` ships on
`/v1/me/activity` and is declared in `RawOverview`. What `activity.ts:353` does
with it is nothing: the label is the hardcoded string
`Last 24 hours · updated ${takenAt}`. Legal today - the gateway rejects any
`window` but `24h` with a 400 - and still a sentence asserting what the payload
states, which is the shape of claim principle 6 is about.

**`GET /v1/me/tools` answers the rest, and the app has never called it.** It
serves `ToolActivity { tool, firstSeenAt, lastSeenAt, requests, failures }` for
**every tool in one request**, and its `tool` slug "matches
`registry::ToolId::slug` in the desktop app, so one tool is one row here and one
row there". `lastSeenAt` is AG-584's last routed request. It shipped 2026-08-19,
in the same PR as the overview - two weeks *before* the tray's message half was
built on the premise that a per-row fan-out was the only option available.

So the cache map, the 45-second TTL and the per-row fan-out were solving a
problem an existing endpoint had already solved, and adopting it retires all
three plus the tray's installations read - the "clean fix" the Not-in-scope
section below has wanted since this plan was written.

**Three things that cost:**

1. **The window is 30 days, fixed**, with no `?window=`. So `requests` is a
   30-day count, not 24 hours. **Product call 2026-09-08: take 30 days and label
   it.** The tray answers "is this tool working", which `lastSeenAt` and
   `failures` serve better than a 24-hour total.
2. **It could not be narrowed to this machine.** `Scope.installId` existed and
   the query applied `installFilter`, but the route took no `?installId=`, so it
   answered org-wide - and putting an org-wide count on a per-machine row is the
   mislabelling the overview's `machineKnown` gate exists to prevent. Fixed in
   **gate#1001**, which also echoes the scope it applied. **A client must treat a
   missing `installation` echo as "this gateway is older than that change, so
   this reading is org-wide"** and not attribute it to this machine.
3. **API-key accounts get a 403** - no user identity, so no role to check
   org-wide activity against. Not a regression: those accounts already get
   `unavailable: no_identity` on every overview section, so the tray shows them
   nothing today.

**2.1, 2.2 and 2.4 are therefore one piece of work, and it waits on gate#1001
being deployed** - not on a decision. They share a source, and the period label
is where staleness belongs: one "updated HH:MM" for the surface, as the window
pane already does it, rather than a per-row disclosure the 368px row has no
width for. Labelling 24 hours now and relabelling to 30 days afterwards would
put the wrong period on screen twice.

### 2.1 The period label - the largest gap

AC: "The compact experience labels the start and end of the activity period or
names the fixed period, such as Last 24 hours." Nothing in the tray states a
period at all.

The figures are per-tool readings from `GET /v1/me/activity` via the cache map
in `activity_cache.rs`. What period that answer covers has to come from the
reading, not from a hardcoded phrase - a label that says "Last 24 hours" over a
figure whose window was something else is exactly the claim principle 6
forbids. Check what `lib/activity.ts` and the contract in
`docs/ag-572-activity-api-contract.md` actually carry, and where it goes on a
368px row given the age is already the line's tooltip.

If the answer names no period, that is a gateway question, not a copy one.

### 2.2 Stale is not labelled

AC: "Unavailable, stale, and loading values are labelled." Unavailable draws
nothing and loading draws a `Skeleton`; stale discloses itself only through
`measuredAt` in the line's `title`. A tooltip is not a label - it is invisible
to a keyboard user and to a screen reader on most platforms, and 2.5 below is
the same complaint.

`plans/new-app-ui-figma.md:2640` records the product call that a held reading
is a feature rather than a warning, and that stays. The AC asks for a label,
not a warning.

### 2.3 DONE 2026-09-08 - pending change names the route in use

AC: "A pending change shows Needs attention with Reopen required, the route in
use, and Reopen tool."

Two thirds of it was already built and the third was one field away. The row's
status line says `Not protected - Reopen required`, and AG-566's `ReopenCard`
(added to the tray by #233) carries a **Reopen tool** button - the AC's exact
label. What was missing was the route: the card said "on the route it started
with", which describes an address without saying which.

`Verdict.route_in_use` is that address, and it is set *exactly* when the reason
is `reopen_required` - which is this card's whole population - so
`reopenPending` was already reading the verdict and dropping the field.

**Named only when one tool is waiting.** Two tools can be on two different
routes, and one address under both their names would be wrong about at least one
of them; the phrase is true for any number, so it stays as the fallback.

**Not a fourth row line**, which is what this plan first assumed. The frames
draw three, the card is where the sentence about routes already lives, and it
has the width to print an address.

### 2.4 "Last routed request"

AC: "its last routed request, request count, and alert count". Rows show
`status.since` - how long the row has been *protected* - which is a different
fact from when traffic last flowed. Whether the activity reading carries a
last-request timestamp is the same question as 2.1 and gets answered with it.

### 2.5 Keyboard and assistive technology - the real hole

AC: "Platform keyboard and assistive-technology controls can open, read,
navigate, and close the tray popover." Today, per the flow audit:

- **No close.** No `Focused(false)` arm exists anywhere in `src-tauri/src/`,
  though two comments claim one does (`lib.rs:2406`, `:3169`). No Escape
  listener in `Tray.tsx`/`TrayApp.tsx`. With `alwaysOnTop: true` the only exit
  is a return trip to the tray icon.
- **`POPOVER_PINNED` is stored at four sites and read at none** (`lib.rs:1287`,
  `:2400`, `:2411`, `:3452`, `:3816`); its `pinPopover`/`unpinPopover` commands
  are called only from `src/App.tsx`, the retiring shell. Dead machinery that
  only makes sense alongside a blur-dismiss. Use it or retire it - leaving it
  is what made the missing dismiss hard to read.
- **No focus management on reveal**, so a keyboard user reaching the popover
  has nowhere to land.
- **The menu has no keyboard navigation and no outside-click.** It is
  `absolute bottom-12 right-4 z-10` over the list (`Tray.tsx:388`), so a click
  on a row still visible beside it toggles that app's routing with the menu
  open. It has `role="menu"` and `role="menuitem"` and none of the arrow-key
  behaviour those roles promise.

**Blur-dismiss landed 2026-09-08**, asked for directly during the manual test.
It had been deferred for a stated reason (`plans/new-app-ui-figma.md`: it needs
pin coordination around OS dialogs like cert trust, plus a tray-click race
guard, neither verifiable from this machine) - both of which turned out to be
exactly what `POPOVER_PINNED` and a 400ms grace window handle. Details in the
Landed section below.

That left Escape, focus-on-reveal and menu keyboard navigation, none of which
needed any of that machinery. **All three landed 2026-09-08:**

- **Escape** dismisses the popover, and closes the menu first when one is open.
  Registered in the bubble phase deliberately: `useFocusTrap` handles Escape in
  capture and calls `stopPropagation`, so a dialog over the popover consumes the
  key before the shell sees it - which is what should happen. Capture here would
  race the trap and sometimes hide the window out from under an unanswered
  config-overwrite confirmation.
- **Focus on reveal.** The window is shown rather than created, so nothing moved
  focus: a keyboard user opened the popover and their focus was still in the
  window behind it, which made the tray readable by assistive technology and not
  operable. Focus goes to the popover root rather than the first control -
  landing on "Expand app" would announce a button with no surface attached and
  put a window swap one Return away.
- **The menu keyboard-navigates**, which `role="menu"` had been promising for a
  fortnight. Arrows wrap at both ends, Home/End jump, Escape closes, and the
  first item takes focus on open - without which Tab walked the list *behind*
  the menu, since the menu opens from a button that keeps focus.
- **A click outside closes the menu and does nothing else.** An invisible scrim,
  because the real bug was not the missing dismissal: the menu sat over the app
  list, so clicking a row beside it toggled that app's routing while the user was
  trying to dismiss something. The design draws no scrim and this one paints
  nothing, so it is not a visual deviation.

**Still open on 2.5:** an audit of what a screen reader actually announces on
this surface, which is a different job from making the controls reachable.

Highest-risk item across the three tickets, and it touches the same Rust the
AG-582 PR edits - so if the ordering has to change, this is the piece to pull
forward.

### 2.6 Refresh must not move focus or announce

AC: "Metrics update while the popover is open without moving focus or
announcing a refresh when no displayed value changes." The 5s poll
(`TrayApp.tsx:148-161`) and the TTL refresh both repaint rows under the user.
Needs an aria-live audit of `ActivityLine` and `StatusLine`: nothing there sets
a live region today, which is probably already correct, but "probably" is not
an audit. The skeleton -> figure transition is the case to check.

### 2.7 Clickable rows and alerts

AC: "Selecting a tool opens its tool detail. Selecting an alert opens the
corresponding event or security-feed context." Consumes PR 1's intent:
row -> `{kind:"app", slug}`, alert half -> `{kind:"security"}`.

The row is the awkward part: it already carries a switch, so the row body
becomes the button and the switch stays a separate control inside it. Nested
interactives - get the markup right rather than putting an `onClick` on the
`li`.

## PR 3 - AG-598: access help and support

Two ACs are already met and stay met: the About area with version, Check for
updates and Replay tutorial (`SettingsPane.tsx:518-534`), and the
recoverable-error rule - `openLink` (`NewUiApp.tsx:993`) routes every opener
failure into the dismissible `actionError` banner, which navigates nowhere.
That last one is cited in the code as being what this ticket is about; keep the
comment.

**The URLs arrived 2026-09-07:**

| Destination | URL |
| --- | --- |
| Documentation | `https://docs.constellationgate.ai/` - unchanged, already `GATE_DOCS_URL` |
| Contact support | the dashboard **Overview** page, where a support floating action button sits bottom-right: `https://app-staging.constellationgate.ai/overview` on staging, `https://app.constellationgate.ai/overview` on production |

Both match the opener ACL's existing `https://*.constellationgate.ai/*`
pattern, so no capability entry is added - and the bespoke
`https://constellationnetwork.io/support` entry in
`src-tauri/capabilities/default.json` can be **deleted**, which is the ACL
getting smaller rather than larger. Keep the trailing-path discipline
`config.ts:47-57` documents: `/overview` satisfies the pattern's literal
separator, a bare origin would not.

Two consequences that are not just a constant swap:

**(a) The dashboard host has to become environment-aware, and today it is not.**
`GATE_DASHBOARD_URL`, `GATE_API_KEYS_URL`, `GATE_POLICIES_URL` and
`GATE_SAVINGS_URL` all hardcode `app.constellationgate.ai`, while the *gateway*
is switchable both at build time (`VITE_GATE_DEFAULT_BASE_URL`) and at runtime
(`GATEWAY_SERVERS`, Settings -> Dev mode). So a developer pointed at staging
already gets production dashboard links from five call sites; support would be
the sixth. `pnpm app:local` defaults to staging, so this is the normal dev
state, not an edge case.

Derive the dashboard origin from the active gateway rather than adding a second
`VITE_` flag - a build-time flag would still be wrong the moment someone
switches server in Dev mode, which is the same class of bug as the hardcoded
host. `gateway-staging.*` -> `app-staging.*`, `gateway.*` -> `app.*`; a local
gateway has no dashboard, so those actions need the "required identifiers"
treatment §3.5 describes rather than a guessed URL. This is the one piece of
AG-598 worth landing on its own if the PR gets large.

**(b) A support FAB cannot receive a diagnostic reference - and that is
accepted.** §3.4's AC wants Send diagnostics now to mint a reference the
support flow can optionally attach. Opening a dashboard page whose support
widget lives in its bottom-right corner gives us no channel to hand a reference
to, so the "separate choice in the support flow" that AC describes happens
inside somebody else's widget.

**Product call 2026-09-07: not a blocker.** Opening the dashboard is the
shipping behaviour for AG-598, and attaching the reference is left to a later
iteration. So §3.4 is out of scope rather than blocked, and §3.3 is done: the
entry opens a page that works. Since AG-603 already mints and *shows* the
reference, the nearest honest version of the AC is the one that already ships -
the user has a reference to paste into whatever the widget asks. A later pass
would need that widget to accept one; do not invent a query parameter in the
meantime.

### Landed 2026-09-07: the env-aware dashboard host

Done ahead of the rest of AG-598, since five call sites were already wrong and
support would have been the sixth.

- **`src/lib/dashboard.ts`** (new): `dashboardOrigin` maps the gateway's first
  host label (`gateway` -> `app`, keeping the environment suffix, so
  `gateway-staging` -> `app-staging` and a future `gateway-dev` needs no edit),
  and `dashboardLinks` builds `root` / `apiKeys` / `policies` / `savings` /
  `support` / `message(id)` from it. An unrecognised or non-Gate host returns
  `null` rather than guessing. `NO_DASHBOARD` lives here too so the window and
  the tray cannot describe that state differently.
- **The four constants and `GATE_SUPPORT_URL` are deleted** from `config.ts`,
  which now carries the note explaining why they were wrong. `GATE_DOCS_URL`
  stays a constant: documentation is not per-environment.
- **The ACL got smaller, then got anchored.** `https://constellationnetwork.io/support`
  is removed from `src-tauri/capabilities/default.json`. The wildcard host
  patterns went with it, on review (2026-09-08): **`glob`'s `*` crosses `/`, so a
  leading wildcard is not host-anchored at all.**
  `https://evil.example.com/a.constellationgate.ai/b` satisfies
  `https://*.constellationgate.ai/*` - verified against glob 0.3 and
  tauri-plugin-opener 2.5.4, which matches with `glob::Pattern` over the raw URL
  string. The suite's own "does not allow an unrelated host" case passed while
  this was true, because it used a bare origin with nothing after it.
  `require_literal_separator` would be the other fix and is not available: the
  plugin calls plain `Pattern::matches`.
  So both capability files now spell out the three hosts the opener is ever
  handed - `app`, `app-staging`, `docs` - and `config.test.ts` carries the
  adversarial rows that fail against the old patterns. Enumerating is safe
  *because* those assertions derive their URLs from `GATEWAY_SERVERS`: adding an
  environment fails a test rather than silently leaving its dashboard
  unopenable.

  **`https://*.amazoncognito.com/*` has the same shape and is deliberately left
  alone.** Raised rather than decided. It backs OAuth sign-in, whose hosted
  domain is a build-time variable (`vars.GATE_COGNITO_HOSTED_DOMAIN`, today
  `swarm-deck-{production,staging}-ue1.auth.us-east-1.amazoncognito.com`) rather
  than a repo constant, so enumerating it would put deployment values in the
  ACL with no test to catch drift - and the failure mode is a sign-in button
  that silently does nothing, which is worse than the exposure it removes. Note
  the exposure is bounded here: that URL is built in Rust from the build
  constant, so it is only reachable by a renderer that can already call
  `openUrl` with an arbitrary string - which is precisely the threat model the
  ACL exists for, hence raising it rather than closing the file on it.
- **Every call site now derives.** The window (`openDashboard`, plus
  `openGapLink` for AG-576's notices, whose `ActivityGaps` takes the action
  *kind* now rather than a URL - neither the environment nor whether a
  dashboard exists is knowable at module scope), the tray, and the legacy
  popover screens: `FirstRun` derives from the gateway the user is signing into,
  which is the worst place to get it wrong - it was sending a staging user to
  the production dashboard to fetch a key that would not work; `Home` and
  `OrgPicker` take the URL as a prop from `App.tsx` and drop the affordance when
  there is none.
- **Contact support is wired, and `TrayMenu` gained the entry** (`744:38201`)
  so both drawn menus finally agree. `SettingsPane` stays without a row - no
  frame draws one, which is a different reason and survives.

**Two stale-closure bugs the e2e tests caught, worth remembering.** The tray's
`onMenuSelect` had `[]` dependencies, so it closed over the first render's
`null` account and would have shipped as "this gateway has no dashboard" on
every click - the derivation was right and nothing reached it. The window had
the same shape once `openDashboard` entered `onMenuSelect` and `toolEventRows`,
and fixing it surfaced a genuine ordering constraint: `toolEventRows` is built
~400 lines above where `openDashboard` was declared, so `openLink` and the
`dash` memo are now hoisted beside the `account` state they derive from. A unit
test on the mapping would have passed through both bugs.

**Two more things landed with it, both asked for during the manual test.**

*Click-outside dismisses the popover.* `POPOVER_PINNED` was written at four
sites and read at none; it is now the reader it was waiting for, holding the
window open across the first load, a system dialog the popover raised, and an
in-app decision in progress. The startup pin is the one that would have gone
unnoticed: Rust sets it before revealing at launch, and only `src/App.tsx` ever
released it, so `TrayApp` would have stayed pinned for its whole life with
blur-dismiss silently dead. A 400ms grace window keeps the tray icon able to
dismiss - the click blurs the popover first, and the icon handler would
otherwise re-open what it had just closed.

*The organization line opens the selector* (§1.2), by handing over to the
window rather than growing a selector at 400px. `request_switch_org` is a
single-purpose stand-in for §1.1's general intent and should collapse into it.

Two things about it worth keeping, both from review:

- **A single-org account opens no picker.** `openSwitchOrg` declines to ask a
  question with one answer, which is right, and it used to return nothing - so
  the hand-over closed the popover, brought the window forward and showed
  nothing at all, for what is most accounts. It now reports whether a dialog
  opened and the handler lands on Settings when none did. The tray cannot gate
  on this itself: the org count is not on `Account`, and reading it per open
  would be a network call the popover does not need.
- **Under `gcNewUi(false)` this control does nothing.** The tray icon always
  opens the `tray` window and so always renders `TrayApp` (`main.tsx`),
  whatever the shell flag says - but the main window then renders `App`, which
  has no `switch-org-requested` listener. So on the retiring popover shell the
  footer reveals a window and stops there. Acceptable while that shell is an
  escape hatch, and written down so it is not rediscovered as a bug.

**And one bug this shipped and the manual test caught.** The tray has its own
capability file, and `tray.json` allowed two *literal* hosts - so the derived
staging URL was refused and Contact support answered "Not allowed to open url
..." from a menu item that looked wired. `config.test.ts` had only ever parsed
`default.json`, which is why 769 green tests said nothing about it. It now
checks every capability granting `opener:allow-open-url`, and the fix is one
`app-*` pattern rather than an entry per environment, so a new gateway fails a
test instead of quietly breaking the popover.

Chasing that also corrected something this file would otherwise have got wrong:
**`glob`'s `*` crosses `/`**, verified by running the real crate. The
path-segment reading says every `/messages/:id` link in the app is forbidden,
and "fixing" that would have been a day spent on a non-bug.

Coverage: 17 unit cases in `dashboard.test.ts`, `config.test.ts` now asserts
the ACL for **every** destination on **every** gateway in `GATEWAY_SERVERS`
(rather than two production URLs) and that the removed entry stays removed, and
`e2e/new-ui-dashboard-links.spec.ts` plus two tray cases pin that the shells
actually thread the account through to the opener. 769 unit, 218 e2e, `tsc`
clean on both projects.

### 3.3 Contact support

AC: available from Settings and each recovery state that may require support.

`GATE_SUPPORT_URL` 404s (verified 2026-08-26). Settings has no Support row and
no Settings frame draws one, which is recorded as a separate decision from the
topnav's (`Topbar.tsx:43-44`). The topnav entry ships knowingly broken by the
2026-09-04 decision.

**Three surfaces, three different answers, and that is the thing to fix.** The
`topnav/menu` component (`744:37692`) and the tray's footer menu (`744:38073`,
item `744:38201`) both draw Contact support. `Topbar` ships it; `TrayMenu`
(`Tray.tsx:455`) omits it on the older "an entry opening a 404 is worse than an
absent one" argument that the 2026-09-04 decision overruled for the topbar and
nobody carried across; Settings omits it for a genuinely different reason (no
frame draws one). Whatever the address turns out to be, the two menus should
agree, and the reason Settings differs should stay written down where it is.

With the address settled: `GATE_SUPPORT_URL` becomes the env-aware
`<dashboard>/overview` from (a), its bespoke ACL entry is deleted, and the
warning block at `config.ts:84-106` is rewritten - it currently tells the next
reader not to wire this up, which stops being true. `Topbar`'s docstring
(`:34-40`) says the same and needs the same treatment.

Then: `TrayMenu` gains the entry so the two menus agree. The recovery states
that may require support already grew one under AG-566 - the interrupted-routing
flow has a `contact_support` action - and it arrived pointing at the address
that 404'd, so it is now on the derived one. Settings stays without a row unless
design draws one; that omission has its own reason and keeps it.

Worth saying in the copy or the label that support lives on the dashboard: the
menu item reads `Contact support` and opens a page whose support control is a
floating button in the corner. A user who does not spot it has been handed a
dead end wearing a working button, which is the failure mode this whole ticket
is about.

### 3.4 Diagnostic reference

AC: "Contact support can include a diagnostic reference created by Send
diagnostics now. Attaching the reference requires a separate choice in the
support flow."

**Most of this landed under AG-603 while this was being planned** (#228,
2026-09-07). `lib/diagnosticsUpload.ts` sends one report on demand and hands
back a `GC-XXXX-XXXX` reference; the destination is PostHog rather than the
gateway, because the gateway has no ingest route and a reference nobody can
resolve is not a reference. So "created by Send diagnostics now" is done, and
this section is only about the *attaching*.

Which is the half that cannot be built as written: opening a dashboard page
whose support widget lives in its bottom-right corner gives us no channel to
hand a reference to. The "separate choice in the support flow" the AC describes
happens inside somebody else's widget.

The "separate choice" is the part to get right: sending diagnostics and
attaching the reference to a support request are two consents, and principle 1
says the user should be able to see where their data goes. `diagnosticsReport.ts`
documents what is excluded; whatever this ships with must not quietly widen it.

### 3.5 Dashboard context

AC: "A dashboard action opens the selected organization and matching
installation, tool, event, or activity when Gate Connect has the required
identifiers."

`messages/{id}` deep links work (`NewUiApp.tsx:2177`). Org and installation
scoping does not, and `config.ts:64-71` records why: the dashboard resolves the
active org from its own session, so a client-supplied org id in the path would
be ignored or would disagree with what the user is signed into there.

That is a product constraint, not missing code. Raise it: either the dashboard
grows an explicit `?org=` selector - the constants become builders, which that
comment already anticipates - or the AC's org clause is unbuildable and the
ticket should say so. The tool and activity clauses may be reachable today;
check what paths the dashboard exposes.

The "when Gate Connect has the required identifiers" qualifier is doing real
work: absent an identifier the action must not open a wrong page. The
`machineKnown` gate in the tray's installations read is the precedent - a null
`installId` means org-wide, and the tray had to gate on it to avoid putting the
whole org's traffic on one machine's rows.
