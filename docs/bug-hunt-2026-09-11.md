## 1. Two concurrent writers to one file lose BOTH writes - FIXED

Branch `fix/atomic-write-race`, commit `fd9a89d`.

Seen in the launch log, never on screen:

    [gate] writing the verdict log failed: creating tempfile
      .verdict-log.json.gate-connect.14358.1789104113530081000.tmp: File exists
    [gate] writing the verdict log failed: rename
      .verdict-log.json.gate-connect.14358.1789104113530081000.tmp -> verdict-log.json:
      No such file or directory

`primitives::write_file` named its tempfile `{file}.gate-connect.{pid}.{nanos}.tmp`.
`SystemTime::now()` is not guaranteed to advance between calls and on macOS
routinely does not, so two writers in one process built the same path.

The collision alone was survivable; the cleanup is what lost data. The writer
that lost `create_new` ran `fs::remove_file(&tmp)` on its way out, and that
tempfile belonged to the winner, so the winner's rename then failed `ENOENT`.
Two writers, zero successful writes.

It fires at launch because both webviews sweep verdicts at once and
`record_sweep` writes from each, on the Tauri threadpool, in one process. The
verdict log backs the rail's status lines and the recovery summary, so a dropped
write is a stale status rather than only noise. Every caller of `write_file`
shares the hazard.

Fixed with a per-process `TMP_SEQ` counter in the name. Pinned by
`concurrent_writes_to_one_path_all_succeed`, which against the old name loses 50
of 1600 writes.

## 2. A tool with no binary is still reported as installed - OPEN

`crates/core/src/integrations/codex.rs:254`

```rust
fn detect(&self) -> Result<bool> {
    let (well_known, names) = self.binary();
    if binaries::resolve_binary(well_known, names).is_some() {
        return Ok(true);
    }
    Ok(env::codex_config_dir()?.exists())
}
```

The second arm reports a tool as installed whenever its **config directory**
exists. A config directory outlives the program that wrote it, so this stays
true after an uninstall, after a broken install, and whenever another product
creates the directory. On the machine this was found on, `CODEX_HOME` is set by
Orca to its own runtime home, so the directory exists unconditionally.

### What it produced

With no `codex` binary resolvable anywhere on the machine - not at
`/opt/homebrew/bin/codex`, not at `/usr/local/bin/codex`, not on `PATH`, not in
`binaries::shell_bin_dirs()` - Gate:

1. listed Codex as installed,
2. offered to route it, and rewrote its config when the switch was flipped,
3. found a running process and offered to close it,
4. closed it on the user's acceptance,
5. told the user to reopen it themselves.

The user then ran `codex` and got `zsh: command not found`.

### The second half: the reopen promise names no way to keep it

`RunningAgent.can_reopen` is `false` for every CLI in the registry, which is a
true fact about terminal programs (see AG-566's note in
`plans/new-app-ui-figma.md`). So the flow always says the person reopens it, and
never says *how*. That is fine when the tool is on `PATH` and fatal when it is
not: the sentence is the entire handoff, and it led nowhere.

### Why the fallback exists

Deliberate, and removing it outright would regress. Its comment records that the
old check was the well-known paths alone, "which is why a tool installed
anywhere else was only found through the config-directory fallback below, and a
tool installed but never run was not found at all."

So the fix is not deletion. Options, none chosen yet:

- Keep the fallback for *listing* but refuse the close-and-reopen flow when
  `resolve_binary` found nothing, since that flow is the one that makes a
  promise about relaunching.
- Carry the resolution result on the row, so a config-dir-only detection can say
  so rather than presenting as a normal install.
- Name the binary in the reopen copy when one resolved, which also gives the
  user the command to run.

Needs a product call on what the row should say. Not fixed here.

### 2b. `shell_bin_dirs` misses nvm, which is why the fallback carries the case

`crates/core/src/integrations/binaries.rs:61`

`resolve_binary` searches the well-known paths, then `PATH`, then
`shell_bin_dirs()`, whose whole purpose is the directories "a login shell adds
and a GUI process does not inherit". It lists `.local/bin`, `.npm-global/bin`,
`.volta/bin`, `.bun/bin`, `.deno/bin`, `.cargo/bin` and `.yarn/bin`.

It does not list nvm's `~/.nvm/versions/node/<version>/bin`, which is where a
plain `npm i -g` puts its shims for anyone using nvm - the most common node
version manager. `~/.nvm` is also not covered by any of the seven entries.

So on a GUI-launched build, an nvm-installed Codex, Claude Code, OpenCode,
OpenClaw or Hermes is invisible to `resolve_binary`, and detection falls to the
config-directory arm every time. That is why finding 2's fallback is doing all
the work rather than acting as the backstop it was written to be.

**This changes how the flow must be tested.** `pnpm app:local` launches from a
terminal, so the dev build inherits the developer's `PATH` and *does* resolve an
nvm-installed binary. A double-clicked `.app` does not. A repro run from the
terminal can therefore pass while the shipped build fails, and the difference is
invisible from inside the app.

Candidate fix: add the nvm layout to `shell_bin_dirs`, honouring `NVM_DIR` and
falling back to `~/.nvm`, resolving `versions/node/*/bin`. The `alias/default`
file names the default version when one is set.

### Not related, recorded so it is not re-litigated

The user's `codex` shim was missing for an unrelated reason: an interrupted
`npm i -g @openai/codex` on 2026-08-31 left npm's staging artifacts behind
(`bin/.codex-hq9Rsr9h` and `lib/node_modules/@openai/.codex-Gmcvi8EH`) and never
created the `codex` link, and the 2026-09-03 reinstall skipped the half-written
platform package rather than repairing it. `npm uninstall -g` followed by
`npm install -g` cleared both artifacts and produced a working 0.154.0.

Gate did not cause it and cannot: its only file deletions are `snapshot_path`
and `journal_path`, both inside its own app-support directory, and closing a
tool is a `SIGTERM` by process name.
