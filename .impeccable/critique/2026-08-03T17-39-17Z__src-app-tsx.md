## Priority Issues

**[P0] The popover never re-reads its own state**
- **What:** B mapped every call site. `listTools` / `proxyStatus` / `listProviders` / `routedClientsStale` are read in the mount effect (`App.tsx:261-377`, deps `[]`) and afterwards only by (a) the `proxy-state-changed` listener, which Rust emits from exactly one place - `lib.rs:1674`, after the startup auto-enable - and (b) three user-initiated callbacks. `useWindowReopen` fires `track("popover_opened")` and nothing else. Zero timers in `src/`. So a machine that signed in at 9am shows 9am's truth at 6pm, and the empty state's copy tells the user to "reopen this window", the one action that provably does not refresh.
- **Why it matters:** It voids DESIGN.md's "status is a verb" and PRODUCT.md's "optimize for staying, not starting". A config that drifted externally still shows green; a tool installed after launch never appears; a dead Linux helper leaves "Routing on" in the header. The reassurance is a cached value.
- **Fix:** The machinery already exists - the `proxy-state-changed` handler does a full re-read. Hoist its body into `refreshState()`, call it from `useWindowReopen` and on a slow interval while visible, and emit `proxy-state-changed` from every backend mutation rather than only the startup enable. Then make the empty-state copy name an action that works.
- **Suggested command:** `/impeccable harden`

**[P1] Focus falls out of every takeover at its step boundary**
- **What:** B drove all three panels. `useFocusTrap` binds keydown to the panel element (`useFocusTrap.ts:59`) with deps `[ref]`, so it never re-runs when the step changes. When the focused control unmounts, `document.activeElement` becomes `BODY`, the handler stops receiving keys, and Escape is swallowed - App's own handler bails while `routingNotice !== null`. Verified: dialog still present after Escape in all three. In `RoutingChangeNotice` one Tab from there lands on **"Close everything"**. In `UpdatePanel` mid-install and `QuitConfirm` while busy the dialog has **zero** focusable descendants, so Tab escapes into the `aria-hidden` background and focuses "Settings" and "Route through Gate" - reachable because the background is `aria-hidden` but not `inert`.
- **Why it matters:** This is round 8's `initialFocus` fix left half-done: it anchored mount-time focus and did nothing about the boundary where the danger button appears.
- **Fix:** Bind the trap to `document` so the re-entry branch can fire, re-assert `initialFocus` when the step changes, and mark the background `inert` rather than only `aria-hidden`.
- **Suggested command:** `/impeccable audit`

**[P1] The off-switch track fails 3:1 on subtle rows - my own regression**

I recomputed and confirm. This is not hover-transient: `GroupDetail.tsx:193` is `open ? "bg-gc-subtle" : "hover:bg-gc-subtle"`, so every expanded member row holds a failing switch persistently.

**Sam (screen reader / keyboard):** focus lands on `body` at every takeover step boundary, Escape stops working there, and the next Tab is either the destructive action or a background control the dialog is supposed to have covered. Two takeovers open focus on a control wearing Chrome's ring, not the app's. Each ledger row announces its name twice in two vocabularies. The expanded certificate state clips content with no programmatic signal.

**New machine, mid-task, no provisioned org:** the org-less dead end is now handled well - create, fall back to a key, or sign out. That is the named persona failing on the flow the product is named for.
