## Design Specificity Verdict

**The state machine is authored for this product. The surface is not.**

**LLM assessment.** Unmistakably Gate Connect: the `desired` vs `routed` split in `groups.ts`, which refuses to conflate intent with flow, so an enabled domain behind an untrusted CA reports "Needs trust" rather than green. The `config file` / `proxy` chips in `GroupDetail.tsx:261` are the most product-specific pixels in the app, because showing the mechanism *is* the transparency the product sells. `platform.ts` names two different vaults correctly per OS and takes a determiner so the sentence stays grammatical. That is "credentials are the product" implemented at the level of grammar rather than asserted in a tagline.

Interchangeable: the composition. Sticky header with wordmark, pill and gear; a shadow-bordered card with icon tile and switch; a mono section label; full-bleed rows with title, sub-line, pill, switch, chevron; a hairline footer strip. Rename the strings and this ships as Rectangle, Bartender, CleanShot or any Tauri tray app built this year. Not one structural shape here is unique to Gate Connect. The ledger row in particular is a stock iOS settings row with four trailing elements: DESIGN.md calls it a ledger, and it is not laid out like one. No columns, no cross-row alignment, nothing tabular.

The four takeovers are now geometrically identical by construction, since they share one shell. That is right for consistency and it also means quit-with-tools-routing and an OAuth upsell are the same object with a different sentence. The Gatehouse north star is a small warm room with the key on its hook; the takeover shell is where that image could be built, and it is a generic centred modal.

Does the popover make the user feel where the key lives? Partially, in the weakest register available. On Home the only mention is the pinned footer at 10.5px ink-3 beside a version number and a link: the smallest, faintest type on the screen. Nothing on the Routing card, nothing on any row. The product's strongest claim renders as a status-bar footnote. The one screen that does it well is FirstRun with the key form open, and that screen is seen once.

## Overall Impression

The state model came out of the last pass in good shape, and two of the three things fixed there hold up under rendering: the pill no longer overstates, and the error copy is the strongest thing in the product. What rendering exposes is that the app's problems were never mostly in its logic. They are in its *measurements*: strings that do not fit the boxes they are in, four values where the design system specifies one, and a vertical composition that has never been resolved.

The two P1s are both the same shape, and it is an uncomfortable shape: **a fix was made correctly in one file and never carried to the other, and a comment now describes a state of the world that is no longer true.** That is what drops Consistency to 2.

## What's Working

**The pill vocabulary refuses to round up, and one function guarantees it.** `groupPillLabel` and `memberPillLabel` are exported so the sr-only row description and the switch's `aria-describedby` read the same sentence, and `routed` is defined strictly narrower than `desired`. The header goes green only when `routedCount > 0`. Trust in a credential broker is built by never once being caught overstating, and this makes overstating structurally impossible rather than a matter of care.

**`classifyError` names the button the user pressed.** A cancelled admin prompt raised from the Routing switch says "Flip the Routing switch again and approve your system password prompt", not "Click Connect", which names no control on Home. Errors here arrive from an OS dialog the user half-remembers dismissing, and naming the exact control closes the loop with zero recall.

**Two vaults, named correctly, everywhere.** `secretStoreName` and `trustStoreName` are separate functions because they are separate stores, and the reassurance is worth zero if it names the wrong one. Every claim in the product routes through them, and the codebase treats that as a hard invariant rather than a copy detail.

## Priority Issues

### [P1] The footer's credential promise truncates, because a two-item strip is carrying three

**Why it matters:** the strip renders the credential line, `v{version}`, and the Gate dashboard button. Measured with real Geist at 360px: 332px content, 112.5px dashboard, ~44-50px version, two 8px gaps, leaving the credential text **136-142px**. `Key in your keychain` is 118.5px and fits. `Session in Credential Manager` is 146px and does not. `Key in your system's secure store` is 159.2px and does not, which is what every platform renders during the first async tick before `usePlatform` resolves. So on Windows with OAuth the app's core promise reads `Session in Credential Manag…`.

The comment directly above the code already reasons about this: it says `secretStoreName` drops the possessive on Windows "and only there, which lands it at 146px with all six platform / auth-mode combinations clear." That tuning assumed a 153px slot. Putting the version back took 16-18px of it and the fix silently broke. A second comment in the same block still claims "The version moved to Settings > Help; two items is all this strip can carry at 360px" — and I confirmed Settings has no version anywhere. The code contradicts its own comment, and the comment is right.

**Fix:** drop the version from the strip and actually put it in Settings > Help, as the comment claims. Cheaper than the alternative and matches stated intent. If the version must stay pinned, make the dashboard an icon-only `IconButton` with `aria-label="Gate dashboard"` to recover ~80px. Either way, re-measure all six platform × auth-mode combinations before landing.

**Suggested command:** `/impeccable polish`

### [P1] The gateway host truncates in the header in most states, and Settings already fixed this exact bug

**Why it matters:** `PopHeader.tsx:33` puts the host in the same flex row as the pill and the gear, as a `truncate` span. Measured slot against `gateway.constellationgate.ai` at 176.4px: "Routing on" leaves 181px (fits, 5px margin), "Routing off" leaves 180px (fits, 3px), **"Needs trust" leaves 176.2px (truncates)**, **"Nothing routing" leaves 156.7px (truncates)**, **"Nothing to route" leaves 152.8px (truncates)**. Confirmed in the captures. `gateway-staging.constellationgate.ai` is 226.8px and truncates in every state.

The truncation is worst in exactly the states that mean something is wrong, which is when a developer most needs to confirm which gateway they are pointed at. And note the second-order effect: the "Nothing routing" label added in the last pass is 108.3px, wider than "Routing on" at 83.7px, so **fixing the pill's honesty made the host truncation worse**. That is a real cost of the previous change and it was not measured at the time.

`Settings.tsx:351` fixed the identical problem, with a comment reasoning about it explicitly, by moving the host to a full-bleed line beneath the row. The remedy was never carried to `PopHeader`, which is on every screen.

**Fix:** apply the same remedy in `PopHeader` — host on its own full-width line below the header row — or reserve a fixed host slot and let the pill truncate instead. While there, reconcile the two alignments: `PopHeader` indents the host `pl-[25px]` to sit under the wordmark, `Settings` leaves it flush at `px-3.5`. Same string, two treatments.

**Suggested command:** `/impeccable layout`

### [P2] A failed `proxyStatus()` is a silent, actionless dead end

**Why it matters:** verified at `App.tsx:897` — `showProxy = proxy !== null`, and the startup path sets `px = null` after `trackError(err, "startup")` and nothing else. Home then hides the entire master Routing card, `proxyOn` is permanently false, `memberFromTool` computes `routed = connected && proxyOn` so every row reads Not routed forever, and the header locks to "Routing off". No `ErrorNote` renders; the failure reaches PostHog and no human. The user sees an app that says routing is off, offers no switch to turn it on, and will never go green. Given that the success metric is sustained daily routing, this is precisely the churn state.

**Fix:** when `proxyStatus()` rejects at startup, render an `ErrorNote` on Home with the classified failure and a Retry, instead of silently hiding the master card. `classifyError(err, "proxy_toggle")` already produces sensible copy.

**Suggested command:** `/impeccable harden`

### [P2] The credential reassurance is the faintest thing on every screen, and absent from Home's body

**Why it matters:** the promise renders at 10.5px `ink-3` with an 11px glyph, in a hairline strip, beside a version number. It is the smallest type in the app, and on Home it is the only mention of the keychain. A 10.5px footnote does not produce a feeling, it produces a status bar. This compounds with the peak-end problem below: the session's last impression is a caveat about stale agents, not "the key is safe and traffic is flowing."

**Fix:** two cheap moves. Give the Routing card's sub-line a third clause when everything is healthy (`On · 3 of 3 routing · key in your keychain`), putting the promise at 11.5px inside the screen's primary control. And when `routedCount === routableCount && !partial && banner === null`, close Home's empty tail with one quiet confirming line instead of dead white. The footer can then shed the credential line and carry version plus dashboard cleanly, which also resolves the first P1.

**Suggested command:** `/impeccable clarify`

### [P2] The vertical composition is unresolved: half-empty rooms on four screens, a clipped row on the one that matters

**Why it matters:** rendered at real height, GroupDetail with two members has ~330px of white below the last row, Settings ~300px below Reset, OrgPicker ~200px, Home-when-routing-off ~90px. Meanwhile Home at 520px with the startup banner clips its fourth ledger row in half under the footer, and the only affordance is a 6px `ink-300` thumb at 1.9:1 on white, invisible under macOS overlay scrollbars. A user who never scrolls Home never learns the fourth family exists. DESIGN.md's One Room Rule promises a composed 360×520 panel; what renders is a web page in a small window.

**Correction to the diagnosis:** Assessment A attributed the dead white to the `key={screen}` motion wrapper added in the last pass breaking flex parenting. I checked, and that is not the cause. `.gc-scroll` has no `display:flex` rule in `index.css` — it carries only a focus `scroll-margin` — so `Settings`' own `flex grow flex-col` never had a flex parent, before or after the wrapper. `grow` was already inert and `mt-auto` already had no free space to consume. The wrapper added a block layer and changed nothing. The defect is real and pre-existing; the causal story is not.

**Fix:** make the screen wrapper `flex min-h-full flex-col` so `grow` and `mt-auto` do what their authors intended. Separately, add a bottom fade or a persistent scroll shadow on `.gc-scroll` when `scrollHeight > clientHeight`, so a clipped row reads as "more below" rather than a rendering fault.

**Suggested command:** `/impeccable layout`

## Emotional Journey

**Peak:** FirstRun with the key form open. "Saved to your keychain. Your config files get the gateway URL, never the key." The thesis of the product, in plain language, at the instant of maximum anxiety.

**Peak, unexpected:** the quit takeover naming "Claude Code and Codex" specifically and offering to restore their own settings for the downtime.

**The end is wrong, and this is the highest-leverage finding in the report.** Peak-end says the last thing matters as much as the best thing. In the most common state — routing restored at launch with agents that predate it — what a user closes the popover on is a three-line banner reading "Routing is on. Anything already open isn't routing through Gate yet." The session ends on a caveat about what is *not* working. The emotional target is "good, that's handled"; the closing note is "something you own is still stale." The banner is correct and honest. It is also the last impression, and there is no counterweight anywhere on the screen stating the thing that *is* handled.

**Valleys.** Signing in is the highest-stakes moment and the app is at its quietest: FirstRun hands off to a browser, and you return to OrgPicker, where nothing says what was stored or where. Routing-off Home shows an indigo on-switch, a grey pill and "waiting on routing" together, above ~90px of dead white, so a deliberately paused app looks broken. The `showProxy` failure is a dead end with no error at all. Flipping the master switch puts `cursor-wait` on every element and then replaces the whole room with a takeover.

**Degraded state is the one valley the design climbs out of:** amber "Needs trust", a card naming the reason, and the Trust button on the card face rather than behind the disclosure.

## Questions to Consider

1. **What if the ledger were an actual ledger?** DESIGN.md calls it one and the rows are stock settings rows. Four data points per row (family, count, pill, mechanism) as columns with cross-row alignment and tabular mono numerals is the one structural move no neighbouring tray app would make, and the design system already asked for it.
2. **Why does the key never appear on Home?** Settings already holds the prefix. If the Routing card showed the first characters in mono beside the shield when everything is healthy, "the key on its hook where you can see it" would be rendered rather than described. Or does showing a prefix make people nervous?
3. **Should the master Routing switch exist at all?** It creates the third orthogonal reason a row can be on and not routing, which is the largest single source of contradictory signals in the UI. If flipping any family switch started the engine, what does the master buy that a "pause all" would not, at a fraction of the conceptual cost?
4. **What is the last thing a user should see?** In the most common state it is a caveat about stale agents. If the metric is sustained routing, the closing frame is the highest-leverage pixel in the product and nothing is designed for it.
5. **Four takeovers, one shell, four meanings.** Quit-with-tools-routing and an OAuth upsell are now the same object with a different sentence. Should the destructive ones differ structurally — different entry direction, different anchor, a different relationship to the room behind them?
